# FS25 vault capability audit

Status: **in progress**, 31 October 2026. This audit reopens the question that the 65-entry companion validation matrix could not answer: whether every vault mod with useful, distinct data has an honest Farm Dashboard reading. The completed matrix is evidence for its tested integrations, not a vault-wide pass.

## Inventory boundary

- Current read-only `P:\FS25 MOD VAULT\by-category` enumeration: **8,012 ZIP paths**. The maintained vault index dated 26 October lists 8,011, so it is not an exact current inventory.
- The 23 September source-screening inventory covered **665 ZIP names**. By filename, 602 remain in the current category tree, 63 are absent, and 7,407 distinct current names were outside that older sample. Filename overlap is a triage aid, not proof of identical bytes or versions.
- The read-only `2026-10-31-scan-vault.py` scan covered all 8,012 current category-tree ZIP paths. **1,803** contain Lua and **1,549** declare source files in `modDesc.xml`. **1,201** Lua-bearing ZIP names were outside the older 665-name screen. - `FS25_Bale_Storage.zip` in `uncategorized` was unreadable as a ZIP; its contents and playability are unproved. No vault files were modified.
- A title/category/source-file keyword pass put **118 ZIPs across 91 normalized titles** into an initial review queue. The queue includes duplicate versions, RF packages, native-data overlap and false positives; **118 is not a missing-integration count**. The sortable 1,201-row Lua triage file is `Z:\Graham\agent-comms\farmhub-companion-acceptance\VAULT-LUA-TRIAGE-2026-10-31.csv`. Every row is still a source-review lead, not an acceptance result. Lower-scoring rows must also be assessed before claiming the vault audit exhaustive.

## Decision rule

For each candidate, establish the exact current ZIP hash/version and source-owned state; decide whether that state is distinct from the normal game export, farm-scoped and safely readable; add a bounded collector and visible reading where justified; then compare a fresh nonempty game state, committed export and installed page. Classify native-game overlap and detection-only mods honestly. Never call an empty, unavailable or settings-only result a gameplay pass. RF-owned Ally work has priority; no direct Graham-PC UI use, public release, main push or RF/VPS changes are in scope.

Further source checks for the next candidates:

- Farm Limit Manager v1.0.0.0 has two byte-identical vault ZIPs (`FS25_372370_Farm_Limit_Manager.zip` and `KM_82655_Farm_Limit_Manager.zip`), SHA-256 `58C1005A23CB0F9DB6180DFA0C30877A244ADF115DBFBF6B689307A54E1D24B8`. `g_farmLimitManager.settings` holds five **save-wide** caps (active AI workers, husbandries, greenhouses, factories, contracts), defaulting to one each and persisted in `farmLimitManager.xml`; these are not per-farm settings. Its count helpers take a farm ID for active jobs/contracts and owned placeables. A dashboard could show the save-wide caps beside exact export-farm utilization, clearly distinguishing scope, but native counts alone are not a mod-owned capability. The source has no historical limit-hit or denied-purchase ledger. Classify as lower-priority settings/utilization candidate; a nondefault cap and a real blocked action would be needed to establish behavior beyond static defaults.
- Bale Batch Tracker builds `BaleBatchTracker.snapshot` every 5 seconds (every 1 second with fermenting bales). Its two vault paths (`FS25_374533_Bale_Batch_Tracker.zip` and `KM_83075_Bale_Batch_Tracker.zip`) have identical SHA-256 `C614FF07E8924D9666A731A12DD07B8F7FDEE9DA36C643275C171B16722B3EE6` and are one package. The snapshot includes physical/stored counts and litres, fermentation groups, ready counts and storage rows. Its source takes `g_currentMission:getFarmId()` as the snapshot farm. A collector must require `snapshot.farmId == exportFarmId`; if the mod has no farm ID on a dedicated server, it must report unavailable rather than export an all-farms aggregate. The normal dashboard already has a bale inventory, so the extra value is the mod's grouped fermentation and readiness view, not duplicate totals.
- Net Worth Tracker records `g_nwt_historyManager.histories` on `DAY_CHANGED` and persists those samples. Its record function derives the farm from `playerUserId`; dedicated-server behavior is unproved and may be unavailable. The dashboard can display existing history only after filtering by an exact farm ID; it must not manufacture historical points from its current net-worth estimate. The mod's value calculation includes money, debt, equipment, land, placeables, livestock and stored fill, which may differ from Farm Dashboard's current estimate.
- The gameplay `FS25_339475_FS25_netWorthTracker.zip` and uncategorized `GH_EvanKirsch__fs25-nwt_FS25_NetWorthTracker_update.zip` are both v1.1.0.3 with identical non-`modDesc.xml` member bytes. Their archive hashes differ (`00A27FC7A8A9A239DC19DE411AF89B28B9F9EE385DCA28D577D4FDE100B974E9` versus `EFFF67FE5E1068AADE475D52245209FF9E3ACF44BF0314B18D5FC250DCF496D1`); the latter changes description/schema metadata, not Lua behavior. Treat as one code capability with two package variants, and test only an exact installed hash. `ITCH_4632292_FS25_SWUNetWorthTracker.zip` is a separate implementation described below.
- SWU Net Worth Tracker v1.0.0.1 (`ITCH_4632292_FS25_SWUNetWorthTracker.zip`, SHA-256 `408C3048ADC749AF9819CD4BF9E5F3E49639AF4DE57F2BA9CF33F1EF4BF4BACF`) is a separate implementation. It stores current asset/debt components and a bounded timestamped history in `g_currentMission.netWorthSystem`, persisted through its config module. The history rows have **no farm ID**; the calculation chooses a farm through the local player, user ID 1, then a fallback to the first found farm. Reading this global as the export farm would be unsafe in multiplayer and may be wrong even in a multi-farm save. Do not merge it with Evan Kirsch's farm-keyed history or expose it as farm-scoped without a reliable runtime identity check. The `src/NWT_historicalData.lua` file is only a placeholder; the actual history writer is `scripts/main.lua`.
- Productions Manager persists `ProductionScheduleManager.data[pointKey][productionId] = { months, scheduleEnabled }` and enforces the schedule on period change. The data itself carries no farm ID. A safe reader must resolve each stable point key to a currently owned production point (the source uses owning placeable unique ID, then numeric ID aliases), omit unresolved/orphan entries, and never call `rebuildRuntimeMap`, `applyAll`, or `commitFromUI`. This schedule is distinct from a line's current on/off state. Empty/default schedules would not be a meaningful gameplay pass.
- Market Price Helper's actual runtime object is `g_priceTicker`. It persists sampled per-fill-type prices with day/hour/period in `history` and keeps averages, alarms and stock. The source creates that instance only when `g_client` exists, so a dedicated server is likely to have no readable instance even though the mod is loaded. Its stock routine returns all farms if no current farm ID is available. Any collector must require an exact current/export farm match, expose unavailability on a headless server, and avoid treating native current sell prices or unscoped stock as new mod-owned value. Historical price samples and alarm selections remain candidates for a bounded single-player reading.
- Implement Usage Counter v1.2.0.0 has seven vehicle specialisations. Cultivator, cutter, mower, plow, sowing machine and sprayer store lifetime `usageCounter` plus `sessionCounter` as worked hectares; bale wrapper stores `lifetimeCounter` and `sessionCounter` as **bale counts**, not hectares. A collector must use only owned vehicles with the exact relevant specialisation, identify those two unit families separately, and retain the mod's resettable session meaning. Native operating hours do not duplicate these counters. Nonzero fieldwork or bale-wrap gameplay is still needed for acceptance.
- Vehicle Inspection (HU) v1.0.0.0 has two vault paths (`FS25_373915_Vehicle_Inspection_HU.zip` and `KM_82788_Vehicle_Inspection_HU_.zip`) with identical SHA-256 `30CF475C88045BD6BFC4B48167A9C780D4F764328DD9BC3FA3CD096975EB558C`; count them as one package. Its `g_huManager.records` is keyed by vehicle unique ID. `ensureVehicleRecord` assigns `farmId` from the currently owned vehicle and stores class, interval, custom interval and remaining months; `getStatus` distinguishes valid/due/overdue; the monthly update decrements remaining months. The mod saves `huSystem.xml` and synchronises state to clients. A read-only dashboard reading can filter exact `record.farmId == exportFarmId` and join to currently owned vehicle IDs, excluding stale or foreign records; due counts and a named vehicle countdown are distinct from native vehicle maintenance. The mod's first scan grants full intervals, so a newly installed default state would prove data flow only, not the due/overdue transition or inspection action. Verify a nonempty owned record and later period behavior before calling gameplay acceptance.
- Realistic Crop Rotation v1.1.0.1 likewise has two identical vault ZIPs (`FS25_370461_Realistic_Crop_Rotation.zip` and `KM_83006_Realistic_Crop_Rotation.zip`), SHA-256 `BC0377AFDA2594C93CF957E13018152262D390429CF5477E0E6A719E8262D280`; count as one package. `RealisticCropRotation.manager.repository` persists farmland-keyed four-entry history, main/cover four-slot plans and last-known active crop in `realisticCropRotation.xml`. The repository has no farm ID on entries. A collector must resolve each farmland ID through `g_farmlandManager:getFarmlandOwner` and require exact export-farm ownership at read time, including after land sale; never export the whole repository or its other-farm plans. Unlike the native current crop view, a filled plan and past rotation entries are distinct mod-owned readings. The mod's menu also calculates disease/rotation advice, which needs separate review before promising it. A newly installed empty plan is detection only; acceptance needs a nonempty owned-field plan/history in game, fresh export and installed page.
- Stall Rental v1.0.0.1 has no ledger, accumulator or persisted per-horse rental state. `StallRental:onPeriodChanged` scans server placeables, accepts horse barns owned by each farm, counts horse clusters whose health is at least 80%, cleans those horses, and posts `qualified × 600` once as native `MoneyType.OTHER`; only optional debug lines contain the event count. A dashboard projection could be useful, but it is a derived current-state estimate, not a read of the mod's previous payout. Do not present it as earned income or count detection as acceptance. A real nonzero period rollover and bank/finance observation would be needed to verify realized payout.
